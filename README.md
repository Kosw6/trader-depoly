### 공유 호스트의 실행 계약



- Go는 작업을 예약하고 Kafka로 전달하며 상태를 관리한다. Python은 수집·변환·적재를 수행한다. 모든 Go replica에서 `WORKER_SHARED_HOST=true`로 독립 워커 용량 planner·Docker/ASG actuator를 제외한다.

- 수집 워커는 1개, 512 MiB·0.5 vCPU 상한으로 시작한다. `/app/pipeline_output` 128 MiB와 `/tmp` 32 MiB tmpfs도 이 메모리 상한에 포함된다. 기존 분리 ETL 소비자와 별도 수집 호스트를 중복 기동하지 않는다.

- 원문은 S3 업로드 후 읽기·해시 검증을 거쳐 보존한다. 작업 상태·값·계보는 PostgreSQL, 전달 상태는 Kafka에 남긴다. 기존 Kafka group·ledger consumer 이름을 유지한다.

- 대량 수집과 대량 재색인은 겹치지 않게 배치한다. 정상 종료는 현재 항목을 마친 뒤 진행하며 S3/SQL 결과가 불명확하면 offset을 확정하거나 무조건 재시작하지 않는다.

- 뉴스 수집기는 후속 개발 대상이다. Spot 노드 자동 대체와 종료 통지 처리까지 이번 변경으로 구현된 것은 아니다.

T3 CPU·메모리 규격은 [AWS 공식 사양](https://aws.amazon.com/ec2/instance-types/t3/)으로 확인했다. 위 두 신규 사양은 초기 용량안이며 동시 사용자 수나 처리량을 보장하는 부하 테스트 결과가 아니다. 비교 부하 테스트에서 CPU 크레딧, 지속 사용률, RAM, 디스크 증가량과 응답 지연을 측정한 뒤 확정한다.



### Go 컨트롤러: 제어 API와 작업 관리



- 기존 `trader-controller`를 별도 호스트에 배치한다. 수집 일정·작업/항목 상태·재시도 관리·커버리지/공백 조회가 역할이다. GPU 추론·임베딩·DB 자체를 이 서버로 옮기지 않는다.

- 초기 자원 예산은 Go API 512MiB 내외, TLS 프록시 128MiB 내외에서 시작하고 측정 후 조정한다. 호스트 4GiB 전체를 애플리케이션 한 개에 할당하지 않는다.

- 연결은 사설 VPC에서 기존 DB/Kafka와 통신하는 방향으로 설계한다. 관리자 8090 포트를 인터넷에 직접 열지 않고 SSM 또는 인증된 관리자 진입 경로를 사용한다. 공개 DB 포트나 새 NAT를 암묵적으로 추가하지 않는다.

- 기존 원본 DB를 다시 켜거나 마이그레이션을 자동 실행하지 않는다. 통합 DB의 실제 파이프라인 스키마·테이블 소유권·최소 권한을 대사한 후 연결한다. 초기 DB 연결 풀은 최대 4, 최소 0을 계획한다.

- 저장소 기본 설정은 스케줄러와 worker manager가 켜져 있으므로 그대로 운영에 복사하지 않는다. 첫 배포는 아래처럼 관찰·조회 우선으로 시작한다. 예전 중단 작업·백필·예산을 자동 재개하지 않는다.



```dotenv

SCHEDULER_ENABLED=false

WORKER_MANAGER_ENABLED=false

RECOVERY_COORDINATOR_ENABLED=false

DB_MAX_CONNS=4

DB_MIN_CONNS=0

ADMIN_COOKIE_SECURE=true

```



현재 PC Python의 KIS 수집·SSM 게시 경로는 이 계획만으로 Go 서버에 이전되지 않는다. 이후 별도 실행 계약과 예산·중단·중복 방지 검증을 거쳐 연결해야 한다.



인프라 켜기/끄기용 `trader-ops`는 이 수집 관리 컨트롤러와 별도 책임이다. [기존 설계](../trader-ops/docs/design.md)의 독립 인증·SQLite·AWS SDK 구조를 유지한다. 추후 같은 Go 호스트의 별도 프로세스로 배치할 수 있지만, 이번에 구현·활성화된 것으로 간주하지 않는다. 현재 계획 때문에 아홉 번째 운영 서버를 추가하지 않는다.



### 모니터링: 관찰과 용량 판단



- Prometheus와 Grafana를 기본으로 하고 로그 수집용 Loki와 알림 판정용 Alertmanager를 함께 배치하는 초기안을 사용한다. 이미지 버전·보안 검토와 digest 고정은 실제 배포 준비 때 수행한다. 기존 예제의 오래된 이미지 태그나 기본 관리자 비밀번호를 그대로 복사하지 않는다.

- 초기 메모리 예산은 Prometheus 2GiB, Grafana 1GiB, Loki 2GiB, Alertmanager 256MiB 정도이며 나머지는 OS·파일 캐시·여유 공간으로 남긴다. 실제 라벨 수·수집 빈도·로그량으로 검증한다.

- 루트 20GiB와 관측 데이터 80GiB를 분리한다. 메트릭 보존은 15일, Prometheus 블록 보존 크기는 40GiB를 초기안으로 잡고 WAL·컴팩션 여유를 남긴다. 로그 보존은 7일을 초기안으로 삼되 20GiB는 로그 공간 예산이며 강제 크기 제한으로 간주하지 않는다. 데이터량에 따라 보존 가능한 기간이 달라진다. [Prometheus 저장소·보존 정책](https://prometheus.io/docs/prometheus/latest/storage/)을 기준으로 설정을 검토한다.

- CPU/RAM/디스크·컨테이너 상태, API 요청량/오류율/p95·p99 지연, DB 연결·느린 쿼리·미완료 거래, Redis 메모리, Kafka lag, GPU VRAM·요청 대기·토큰 처리량을 관측 항목으로 잡는다. 사용자 원문·JWT·API 키·공개 전 개인정보를 메트릭 라벨이나 로그에 넣지 않는다.

- Go 컨트롤러에는 현재 `/healthz`, `/readyz`가 있다. Prometheus `/metrics`가 이미 구현돼 있다고 가정하지 않으며 계측은 실제 배포 단계에서 별도 확인·추가한다. 저장소의 기존 `app-1/app-2`나 과거 공개 IP 수집 대상을 운영에 그대로 사용하지 않는다.

- Grafana 3000·Prometheus 9090 등은 사설/loopback에서만 접근시키고 SSM 또는 인증된 관리자 경로를 쓴다. 서비스의 의도된 중지·유지보수와 실제 장애를 구분해 중지 상태를 계속 장애 알림으로 만들지 않는다. 이메일·메신저 통지 전송은 이번 범위에 없다.

### 합칠 대상과 유지할 경계



- **먼저 비교:** 수집·작업 관리 `trader-controller`를 기존 백엔드 호스트에 함께 배치한다. Go API의 동작/배포는 별도 컨테이너·권한으로 유지한다.

- **관측 독립:** 모니터링은 업무 DB·백엔드와 분리해 문제와 중지를 관찰한다. DB 호스트에 Loki·Prometheus I/O까지 더하지 않는다.

- **별도 설계 유지:** `trader-ops` 인프라 기동/중지는 수집 Go API와 다른 관리 경계다. 이 기능까지 백엔드와 함께 중지시키면 기존 독립 기동 목표와 충돌한다. 필요 시 별도 상시 관리 경계 또는 모니터링 호스트 동거를 인증·IAM 격리와 함께 검토하되, 이번 표가 구현·배포 승인이 되지는 않는다.

- **보존:** 사양 변경·통합을 고르더라도 원본 EBS·작업 상태·KIS 예산을 초기화하지 않는다. 계정에 남아 있는 별도 보존용 서버의 용도를 바꾸거나 삭제하지 않는다.

4. DB+OpenSearch 동시 조회, 임베딩 긴 입력과 배치, 모니터링 cardinality와 컴팩션 시 peak를 확인한다. Loki 포함/제외는 서로 다른 기능 구성으로 표시한다.

5. 현재 중단된 수집을 임의 재개하거나 실제 공급자를 반복 호출하는 부하 테스트를 하지 않는다. 고정 입력·격리된 시험 데이터 또는 읽기 전용 조회를 우선하고, 실제 실행은 별도 요청 범위에서 수행한다.



아직 통합·사양 변경·EBS 이동·서비스 기동·부하 테스트는 실행하지 않았다. 사용자가 선택할 수 있는 사양·역할·비용 비교만 추가했다.
